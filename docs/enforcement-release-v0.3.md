# Enforcement release v0.3

This is an additive publication profile. It does not rewrite or supersede the
historical v0.2 proposal as a record of what was ratified at that time.

## EIP-712 type strings (normative)

The v0.3 mandate binds the isolated signer explicitly. Its canonical type is:

    MandatePayload(uint16 schemaVersion,bytes32 mandateId,address principal,address signer,address vault,uint256 chainId,address target,bytes32 targetCodeHash,bytes4 selector,uint256 maxNativeValueWei,bytes32 purposeKind,bytes32 resourceId,address beneficiary,uint64 durationSeconds,bool recurringAllowed,uint64 validAfter,uint64 validUntil,bytes32 policyHash)

The EIP-712 domain is `Sentinel` version `0.3`. The owner signs the mandate
digest before activation. The Vault checks the owner signature, signer, chain,
vault, active policy, validity window, target, selector, and native-value limit,
then stores that authenticated enforcement state. The isolated signer checks
the mandate's runtime code hash before automatic ALLOW; a mismatch can produce
only a REVIEW, whose execution additionally requires the owner's separately
signed exact-action override. This preserves the established Case 4 recovery
path without letting the isolated signer waive code identity. Signer rotation
clears the active mandate and never transfers mandate authority; it does **not**
revoke outstanding receipts — see "Signer rotation is not receipt revocation"
below.

Receipt, override, mandate, and policy validity use a closed lower bound and an
open upper bound: `issuedAt/validAfter <= evaluationTime < expiresAt/validUntil`.
The action deadline remains inclusive.

Publication identity comes only from
`sentinel.deployment-manifest.v1`, signed by an authority whose address the
verifying party obtains out of band. A bundled `domain.json` is never a trust
root. The manifest binds chain, Vault, owner, signer, deployment block and hash,
runtime code hash, compiler metadata hash, and source archive hash.

The generated [release tree](../release/README.md) contains source, ABI,
bytecode, compiler metadata, a focused adversarial contract test, the runtime,
the independent verifier, and the ephemeral-key cold demo. Assembling it does
not authorize publication, deployment, or push. The cold demo's deployment
authority is generated by the demo itself, signs the demo's own manifest, and is
labelled non-production where it is printed: a self-signed lab loop is never an
out-of-band trust root.

## Signer rotation is not receipt revocation

**Corrected 2026-08-30.** The sentence above previously read "Signer rotation
revokes the active mandate." That is true of the MANDATE and false of everything
a reader takes from it, and `SentinelVault.sol` already carried the correction
the doc contradicted. Recorded here rather than silently reworded.

What rotation does do. `rotateSigner` sets `signer`, clears `activeMandateHash`
to zero, and emits `MandateRevoked`. Because `_checkAction` rejects a zero active
mandate hash, execution stops until the owner exhibits and activates a new
owner-signed mandate naming the new key. Rotation cannot silently transfer
mandate authority.

What rotation does **not** do. **Nothing binds a receipt to the EPOCH in which
its signer was active.** Both receipt checks — that the receipt *names* the
active signer and that it was *signed* by it — are point-in-time comparisons
against whoever `signer` is right now. An adversarial review demonstrated the
consequence: rotate A → B and A's outstanding receipt correctly dies; rotate
B → A and **the same receipt executes again**. The mirror case holds too — a
receipt pre-minted by a standby key is rejected until the owner rotates to that
key, and goes live the instant they do. Receipt currency comes from `expiresAt`
and from the action nonce, not from rotation. Epoch binding is v1.1 work.

The contract states the same thing at the `if (receipt.signer != signer)` check;
grep `Rotation is not revocation` in `contracts/src/SentinelVault.sol`.

## Value at risk: what the per-action ceiling does not bound

Reader-facing because the boundary was previously stated only in the `@dev`
header of `contracts/src/SentinelVault.sol`, which remains the source of truth.

The Vault's hard onchain backstops bound the SHAPE of a single action — target
and selector allowlists, calldata hash, chain and vault binding, nonce ordering,
and a native-value ceiling. They do not bound aggregate loss or execution rate:

- **`maxNativeValueWei` is compared once PER ACTION.** No cumulative,
  rate-limited or velocity bound exists anywhere in `contracts/src`.
- **The drain is atomic.** A relayer contract can call `executeWithReceipt`
  repeatedly INSIDE ONE TRANSACTION — `nonReentrant` stops nesting, not
  repetition. Measured: ~100 sequential valid ALLOW receipts, each at exactly the
  cap, drain a funded vault to zero in one transaction at ~75,700 gas each, with
  `block.number` and `block.timestamp` unchanged throughout.
- **`pause` cannot land during that drain.** Pausing protects only BEFORE
  execution begins or BETWEEN transactions. There is no interval inside the drain
  in which an owner transaction could be included, and nothing to notice while it
  runs.

So a compromised signer issuing sequential nonces drains the vault atomically.
This is an explicitly accepted v1 boundary of a testnet lab, ruled by John
(D-053(a), certified D-054(a)) — not an open defect, and not a promise that a
cumulative or rate bound will be added. The demonstration is
`test_LIMIT_nativeCeilingIsPerActionAndBoundsNoAggregate` in
`contracts/test/SentinelVault.backstops.t.sol`, which the release tree does not
ship; the generated [release README](../release/README.md) carries the same
disclosure for a recipient who has only that tree.

## Value at risk: the policy's allowance ceiling is not enforced anywhere onchain

**Added 2026-08-30 (R-A018-14).** The section above bounds the NATIVE-VALUE
dimension and says nothing about token authority. This is the other half of the
same class, and it is disclosed here for the same reason. It was not
undocumented — §7.1 of the proposal states it at length and
`test_LIMIT_vaultCapsNativeValueOnlyAndNotTokenAuthority` asserts it — but
neither of those travels with a release, so no recipient of the v0.3 tree met
it.

`PolicyPayload.maxAllowanceIncreaseBaseUnits` is a field of the **signed**
policy. It is in the struct at `contracts/src/types/SentinelTypes.sol`, it is in
the EIP-712 type string, and it is inside the `policyHash` that the mandate, the
action and the receipt all commit to. **No contract reads it.** `grep -n
allowance contracts/src/SentinelVault.sol` returns nothing, and the publication
verifier does not evaluate it either — it establishes only that the policy
document supplied is the one the mandate and action committed to.

**The schema itself is the misleading surface, and that is why this is a
comprehension defect rather than only a capability gap.** A reader who meets an
allowance ceiling inside a signed policy type can reasonably conclude an
allowance ceiling is enforced. It is not — not by the Vault, not by the
verifier, and not by anything a recipient can check offline.

One valid ALLOW receipt for `approve(spender, type(uint256).max)` on an
allowlisted target passes every onchain check: pause, chain, vault, nonce,
deadline, mandate, policy, operation, `dataHash`, target allowlist and selector
allowlist. The native-value ceiling never engages, because `valueWei` is zero.
The Vault's entire balance of that token is then transferable by the spender,
for one consumed nonce. Unlimited approval is the flagship Case 2
prompt-injection attack, so **it is refused by the CONFORMANCE EVALUATOR with
nothing behind it** — the evaluator is the only layer that reads the field.

Read alongside the drain above, the shape of the v1 boundary is one sentence:
the Vault's hard caps bound a native-value dimension and no other, so *zero
native value at risk* is not *zero economic exposure*.

This is an explicitly accepted v1 boundary of a testnet lab, not an open defect.
John ruled it at D-042(b): correct the claim now, defer the cap to v1.1, on the
grounds that adding a vault feature the day after S2 is the scope expansion the
project's stop condition exists for, and that a vault-side token cap would
partly mask what the harness is built to measure. A per-action
allowance-increase ceiling is accordingly recorded as **owed** v1.1 work in
`docs/v1-1-register.md` §5 — deferred, not disclaimed — and it is not in this
release. §7.1's containment correction, which carries this row, was certified by
John at D-051(a). The demonstration is
`test_LIMIT_vaultCapsNativeValueOnlyAndNotTokenAuthority` in
`contracts/test/SentinelVault.backstops.t.sol`, which the release tree does not
ship; the generated [release README](../release/README.md) carries the same
disclosure for a recipient who has only that tree. That test asserts the LIMIT
rather than a protection: if a cap is ever added it fails, and the failure is
the signal to correct this section, not to delete the test.

## Publication verifier: execution path and exit codes

**Added 2026-08-30.** Both of these existed only in `verify_publication.py`'s
`--help` output. A caller wiring the verifier into a script reads this document
or the module, not `--help`, and a third exit code that no written surface
mentions is one somebody's `if status != 0` will silently mistreat as a refusal.

`SentinelVault` has exactly two entry points and deliberately no third, and the
verifier is told which one a bundle is presented for rather than guessing:

- `--execution-path automatic` (default) — `executeWithReceipt`. Certifies an
  **ALLOW** receipt only.
- `--execution-path owner-override` — `executeWithOverride`. Certifies a
  **REVIEW** receipt only, and then only alongside an authenticated
  `override.json` naming that exact receipt, action, mandate, policy and nonce
  and recovering to the owner rather than to the isolated signer. A run that
  certifies on this path says so in its headline, per §3.3(2) and D-043: the
  reader must be able to tell *the machine approved this* from *a human was
  asked and signed*.

A **BLOCK** receipt is executable through neither entry point and certifies on
neither.

| Exit | Meaning |
| --- | --- |
| `0` | **Certifying.** Static offline authenticity, with the run's own `NOT ESTABLISHED` line still outstanding. |
| `1` | **Refused.** The reason is printed to stderr as a `FAIL:` line. |
| `3` | **Not certified, and not a refusal.** Emitted only under `--evaluation-time`, which moves the evaluation instant from the machine running the check to whoever wrote the command line (R-A018-03). The run prints diagnostics and certifies nothing. |

## Evaluator check coverage (additive)

The v0.2 §5.7.1 inventory remains the historical baseline. v0.3 adds
`EVAL_MANDATE_SIGNER_ACTIVE`: the signer named by the owner-signed mandate must equal the
Vault's currently active isolated signer. A mismatch is a violation and never produces an
automatic allow. The strict publication verifier independently recovers the owner mandate
signature and the receipt signer signature against the authenticated deployment manifest.

## The evidence and refusal envelopes are still tagged v0.2, deliberately

**Added 2026-08-30 (R-A018-11).** A v0.3 release emits evidence tagged v0.2, and
nothing told the reader why. That is a comprehension problem whatever the reason
for it, so the reason is stated here.

The evaluator's evidence bundle carries `"schema": "sentinel.evidence.v0.2"`
(`ts/src/evaluate/index.ts`), and the refusal record's signing preimage opens
with `sentinel.refusal.v0.2` (`REFUSAL_DOMAIN_TAG` in
`ts/src/signer/eip712.ts`). Both ship in this release, whose publication
profile, EIP-712 domain version and verifier are v0.3.

**The tags are frozen on purpose. D-075 ruled that the v0.3 work changes no
signature preimage, type string, fixture, or sample, and the schema tags are
named in that ruling.** They are not labels on the outside of the envelope:
the evidence tag is a field of the canonical bundle that `evidenceHash` is taken
over, and `evidenceHash` is a field of the signed receipt; the refusal tag is
the first line of the refusal digest's preimage, chosen so a refusal signature
can never be reinterpreted as an EIP-712 receipt signature. Renumbering either
one changes what is signed and invalidates every receipt, refusal, fixture and
sample already issued under it. It is a v1.1 question and not a relabelling.

**What that does and does not license the reader to assume.** Read the tags as
naming the ENVELOPE, not the release that ships it. The bundle's field shape —
§5.6's thirteen fields — is the v0.2 shape, unchanged. What the envelope
*carries* is not frozen with the tag: `policyChecks` is a list of whatever
checks the evaluator ran, so v0.3's `EVAL_MANDATE_SIGNER_ACTIVE` appears as a
row inside a bundle tagged `sentinel.evidence.v0.2`. A recipient reconciling
this tree against the v0.2 proposal should therefore expect the v0.2 envelope
to hold v0.3 content, and should take the check inventory from the section
above rather than from the tag.

**Nothing in this tree is a v0.2 artifact that escaped a rename**, and no
version skew is implied by the difference. If that were ever untrue, this
section is the thing that would have to change first.
