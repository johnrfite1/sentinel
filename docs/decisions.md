- **D-007 (2026-07-27, delegated) — Case 2: what counts as a real prompt injection.** Operationalizes the §7.5 hard gate "a real prompt injection changes the agent proposal and is contained." A demonstration counts as real only when all three hold: (a) the agent configuration is a documented, plausibly-naive default, with nothing in its own instructions engineered to make it obey injected text, and its scaffold pinned by hash; (b) the malicious content arrives through a data channel the agent legitimately reads (§3.1 "retrieved documents"), never through its own instruction channel; (c) a **control run** — same configuration, same channel, benign document — produces the Case 1 proposal. Without the control run the flip is not attributable to the injection, which is the difference between a demonstration and a staged demo. Each injection fixture records model id, model version, temperature, scaffold hash, date, and the full transcript. **Reproducibility:** pinned transcripts are the CI fixtures; one live canary run executes alongside them, never fails CI, and its run history is included in the S2 evidence bundle — an unobserved canary is not evidence. **Spike-first:** the injection is attempted before the deep build, timeboxed to 4 hours. A negative result is a finding, not a failure — §4's claim is that an *untrusted* agent cannot execute, not that a gullible one is fooled. On a negative result: report the frontier-model resistance honestly as its own data point and drive Case 2 with a deliberately naive configuration labeled as such. One genuine injection; no jailbreak research.
- **D-008 (2026-07-27, delegated) — §7.5 soft-gate definitions.** Two §7.5 gates were unfalsifiable as written; under D-003 no implementing agent may define a gate, so they are defined here. **Five-minute comprehension:** three fresh-context reviewers, given only the demo, dashboard, and README — no repository access — each answer five questions frozen before the first run and never shown to the build loop. Pass threshold, set in advance: all three score ≥4/5. The questions are those a skeptical security engineer asks — what is cryptographically bound; who signs what; why Case 3 blocks; what a receipt proves; what it does not prove. Agents run this as a proxy; John samples. **Vendor honesty:** every cell of the capability matrix is documentation-only, dated, and linked to its cited source; the "executed" and "faithfully emulated" columns of the §10.1 labeling scheme are empty in v1 (per D-001); cells that are inference rather than quoted documentation are marked as inference; and no claim *or layout* implying empirical superiority over any named vendor appears in any v1 artifact. The empty-column condition is mechanically checkable.
- **D-009 (2026-07-27, delegated) — Gate S2 pass conditions amended. Amends D-002.** Gate S2 passes on: the full 30–50 fixture corpus; §7.5 hard-gate evidence; the §7.3 ablation report; and the receipt-verifier CLI (D-010). - **D-010 (2026-07-27, delegated) — Receipt-verifier CLI promoted into v1. Amends D-001.** The 14.2 standalone receipt verifier moves from ladder rung 1 to a Gate S2 pass condition (D-009). The reason is engineering rather than strategic: an independent reimplementation is the strongest available test of the spec's precision, and RFC 8785 edge cases, hash-domain separation, and encoding ambiguity surface only when someone builds from the written schema. That feedback is wanted while the schemas are still cheap to change — after the corpus fossilizes, a schema correction regenerates every fixture. **Conditions:** the verifier shares no canonicalization or hashing code with the evaluator (same library behind a different flag is the same code verifying itself); it is implemented in a different language from the evaluator — Python — against an independent JCS implementation and an independent keccak implementation, because cross-language agreement is a materially stronger test than two TypeScript modules *and* is cheaper than hand-rolling a second RFC 8785 implementation; and it is built from the published schemas only. **Effort:** 14.2's 10–20h estimate assumed code reuse. With the independence condition the corrected budget is 20–30h. Recorded as a measured correction to a documented number, per AGENTS.md.
- **D-011 (2026-07-27, delegated) — Fixture-label independence protocol. Extends D-006.** Independence here is **procedural, not organizational**, and §8 states it in those words. A solo build cannot buy organizational independence; what it can buy is an auditable bound. (a) The labeling prompt is authored and frozen **before the corpus build**, and its hash committed. The claim is deliberately "before the corpus build" and not "before the evaluator's failure modes are known" — Case 1 is end-to-end by S1, so some evaluator knowledge already exists; the freeze blocks the bulk of it, which is corpus-build knowledge, from leaking backward. (b) The labeler receives payload schemas, security invariants, and each fixture's declared intent — never evaluator source, never evaluator output. (c) A second fresh labeler re-labels a random ~20% sample; the disagreement rate is reported at S2 as a corpus-quality metric. (d) Thresholds are declared in advance, or the metric is decoration: >10% disagreement halts S2 pending corpus review, and any disagreement on a hard-gate-relevant fixture escalates to John individually regardless of the aggregate rate. (e) John's gate sampling is adversarial rather than random — oversample fixtures where the baseline and conformance verdicts disagree, and fixtures whose label is *review*.

- **D-012 (2026-07-28) — A-011 confirmed: signer refusal semantics, plus a recorded refusal artifact.** John ruled after two outside reviews, both recommending confirmation. The three severity tiers stand, and refusal continues never to become a verdict: "Sentinel evaluated this and blocked it" and "the signer declined to attest" are different claims about what the system concluded, and an evidence bundle conflating them misreports the result. **Added by this ruling:** a refusal must produce a *recorded artifact*, because at present "the signer refused" and "the signer was never asked" are indistinguishable — so Gate S2 could not prove the signer ever saw a request. The artifact is deliberately **not** a DecisionReceiptPayload; a refusal is not a decision, and reusing the receipt type would create something a careless reader could mistake for one. Supersedes A-011, which remains on the record as the original reasoning.
- **D-013 (2026-07-28) — A-012 confirmed as a mechanism, with the CLAIM narrowed.** The per-nonce attestation guard stays, including the basis-scoping narrowing and the rejection of exempting REVIEW. What changes is what may be said about it. It is **per-process, best-effort defence in depth — never a durable system guarantee.** A-012's own stated limits make this unavoidable: the guard lives in process memory, is forgotten on restart, and is blind to a second signer sharing the key. "Sentinel guarantees one live executable attestation per nonce" would be false after a restart, and that is the shape of overclaim §7.5 exists to stop. **The vault's nonce is the actual guarantee.** Any future durable version needs single-writer persistent state before the wording may change. Supersedes A-012's framing; the code is unchanged by this ruling.
- **D-014 (2026-07-28) — A-018 resolved: NO conformance checks in the signer. Bind the signer's own decoding into the evidence instead.** The one fork the two reviewers disagreed on; John ruled for reviewer 1. **Rejected:** giving the signer a narrow decoder that checks resource, beneficiary, duration and recurrence against the mandate. Two implementations of one policy that must agree is a liability rather than a defence — divergence becomes a new failure mode and the more capable one silently becomes authoritative — and a signer checking four fields of many could not honestly be described as independently checking conformance, which is an invitation to overclaim exactly where §7.5 bites. It also could not re-derive simulated effects without re-running the simulation, so the compromised-evaluator threat is only partly addressed. That threat is already answered head-on by ratified work: D-010's independent verifier plus the D-011 labelled corpus. **Adopted instead:** the signer independently decodes the calldata and verifies that the decoded parameters recorded in the evidence bundle match what the bytes actually say, refusing if they disagree. This is *derivation without judgement* — the signer never consults the mandate. Its effect is that the bundle's decoded parameters become signer-attested rather than evaluator-asserted, so a wrong-purpose ALLOW is detectable after the fact by the D-010 verifier, which does the conformance comparison. Accountability without a second evaluator. **Boundary to state precisely and not to overstate:** the signer checks that the parameters match the bytes *given the selector*; it does not check that the selector belongs at that target, which remains the evaluator's job.
- **D-015 (2026-07-28) — A-020 confirmed, and the proposal amended to stop contradicting itself.** `policy.failureMode` governs unresolved checks; §5.2's unconditional "any unknown required check reviews" describes the REVIEW setting rather than overriding the field. The alternative reading would make `failureMode` nearly meaningless. The corollary stands: a target code-hash mismatch is UNRESOLVED, not a VIOLATION, because §4.2 says Sentinel "does not label the target malicious. It reports insufficient evidence for automatic approval." **Two follow-ups ruled with it.** (a) **§5.2 of the proposal is amended** so the prose no longer contradicts the field — leaving the contradiction in place guarantees a future reader re-derives this fork from scratch. (b) **Both `failureMode` configurations must appear in the demo, not only in the tests.** Because Case 4's outcome now turns on a policy setting, a reviewer will reasonably suspect the setting was chosen to produce the wanted result; showing REVIEW and FAIL_CLOSED side by side on the same evidence is what answers that suspicion. Recorded as a demo requirement for §9 step 9.

- **D-017 (2026-07-28) — Independent adversarial review of §9 steps 4–6 is an S1 CONDITION. Extends D-002.** Ruled by John, resolving the gap both outside reviewers identified: only step 3 had had an independent pass, which conflicts with the project's own independent-grader principle (HANDOFF house rule 3, and the playbook's "the generator never grades itself"). **Conditions, as ruled:** (a) the review is fresh-context and adversarial, covering the **S1-relevant portions** of steps 4–6 — not the whole of them, since corpus, ablation and receipt-verifier evidence remain S2; (b) it runs against a **fixed commit**, so findings are attributable and reproducible rather than aimed at a moving target; (c) it reviews the **actual implementation and tests**, not only the evidence summary — a review of a summary grades the summary; (d) **material findings are independently adjudicated**, not resolved by the build loop's own say-so; (e) **confirmed defects are corrected and reverified before S1 closes**. - **D-018 (2026-07-28) — What "end-to-end" means for Gate S1. Clarifies D-002.** Ruled by John at the S1 session, resolving an ambiguity both outside reviewers flagged in the phrase "Case 1 end-to-end". **For S1, end-to-end means: from a CONSTRUCTED exact EVM action, through decoding, simulation, evaluation, isolated signing, vault enforcement, and the resulting onchain state.** Agent proposal generation, and its wiring into that pipeline, belong to **§9 step 7 and Gate S2**. The distinction is not cosmetic: the D-007 spike already showed that an agent *proposal* flips under injection (A-009), but the proposal and the pipeline have never been connected, so a reader who took "end-to-end" to include the agent would be reading a claim the evidence does not support. Recording the boundary here means S1's scope cannot later be quietly widened or narrowed by whoever reads the phrase next. The gate pack and the project gate's coverage boundary both state it in these terms.

- **D-019 (2026-08-15) — Where an agent proposal's calldata comes from. Enables §9 step 7.** Ruled by John at the step-7 design fork, choosing among three presented options. **Ruling: Sentinel ABI-encodes the calldata from the agent's `function_signature` and `args`.** The fork was surfaced rather than settled in code because it decides what a ratified sentence means: §4.2 Case 2 says "Sentinel derives the selector and parameters from calldata rather than trusting the agent's description", and the D-007 agent emits no calldata — it emits typed parameter claims. Encoding from those claims makes the decoder's recovery of them a round-trip through Sentinel's own encoder, not independent corroboration. **Rejected alternatives, with the cost that decided it:** (a) the agent emits raw calldata — keeps §4.2's sentence literally true, but changes `scaffoldHash()` and so stales all four D-007 fixtures, and a naive agent must hand-compute a keccak selector and pad four ABI words, so a mis-encode would break the CONTROL arm and collapse D-007's control-run requirement; (b) the agent emits both, with claim-vs-bytes divergence recorded as evidence — epistemically strongest and the only option that exercises §3.1's "agent-supplied parameter or purpose claims" as a live check rather than a structural impossibility, at the same fixture cost and mis-encoding risk as (a). **Consequences, both recorded in code rather than left implicit.** The transcriber joins the TRUSTED set (§3.1, "canonical schema encoders and hashes"), which makes the encode/decode round-trip test load-bearing: it is the only mechanical check that "the agent proposed X" and "Sentinel evaluated X" are the same X. And what stays untrusted on the agent path is the agent's PURPOSE claim — `rationale` — which reaches no check, no reason code, and no bound field; that is where the Case 2 demonstration now lives, and a test asserts the injected framing never enters the evidence bundle. **§4.2 Case 2 is amended to match**, following the D-015 precedent that prose left contradicting the implementation guarantees a future reader re-derives the fork from scratch. **Revisitable:** option (b) remains available and gets cheaper to adopt before the §9 step 8 corpus fossilises, per D-010's own reasoning about schema changes.

- **D-020 (2026-08-15) — The mandate's purpose fields are compared for EQUALITY, not as ceilings. Clarifies §5.7.** Ruled by John at the facilitated decision session, choosing option (a): *"Let's run with option a for this."* §5.1 gives `durationSeconds` and §5.7 says resource, beneficiary, duration and recurrence are "checked", but neither states the RELATION — which left open whether a purchase for LESS duration than authorised conforms. Both independent labellers (A-026a) labelled the under-duration fixture F016 as BLOCK and both reached it the same way — §5.1 names exactly one ceiling field, `maxNativeValueWei`, and `durationSeconds` carries no `max` prefix — while both flagged the "up to" reading as defensible and unsettled by the text. **The fact that decided it, measured rather than assumed:** `DemoPay.purchase` accepts any non-zero `msg.value` and grants exactly `durationSeconds`; **price does not scale with duration.** So the intuition behind a ceiling reading — that less privilege cannot harm the owner — is false here: a shorter duration at the same price is the owner paying in full for less access, and a longer one is the owner receiving more than they authorised. Neither direction is benign, which is what a ceiling reading would require. **Effect:** the implementation is confirmed unchanged, F016's BLOCK label stands, no re-label and no ablation re-run. **§5.7 is amended** to say the purpose fields are compared for equality and that only fields named `max*` are ceilings — following the D-015 precedent that prose left silent guarantees a future reader re-derives the fork. **Considered and rejected:** renaming the field to carry the rule in the schema. Correct in spirit, but it regenerates every EIP-712 type string and every fixture hash, and would invalidate the sample set the D-010 verifier was just built against — disproportionate to one sentence.

- **D-021 (2026-08-15) — A reverting simulation is a FAILED RULE and blocks. Clarifies §5.2.** Ruled by John at the facilitated decision session, choosing option (a): *"Let's go with path A."* §5.2 as amended by D-015 gives a clean dichotomy — a failed rule blocks, an unknown required check follows `failureMode` — and §5.7 lists "revert or success" as a supported effect, but nothing said which side a revert falls on. **This was the sole inter-labeller disagreement** (A-026b): labeller A read F002 as REVIEW, labeller B as BLOCK, and both independently wrote the ambiguity up as a spec gap before knowing of the other. It is why the D-011(c) rate is 10.0% rather than 0%. **Measured before the fork was put:** all four fixtures where the engine is stricter than labeller A — F002, F037, F038, F044 — block on `EVAL_SIMULATION_SUCCEEDS` and nothing else, so this was one question rather than two; undecodable calldata is already UNRESOLVED and does not cause the block. **Rationale for the ruling:** a revert is a determinate observed fact — the simulation succeeded in reporting that the call does not execute — so nothing is unknown, and §5.2's "unknown required check" does not describe it. **The counter-argument is recorded because it was not fully answered rather than because it lost:** §3.3(7) makes BLOCK remediable only by a new mandate or policy, so under this ruling a mis-set zero value costs the owner a whole new mandate rather than a corrected re-proposal. If field use makes that friction real, this is the entry to revisit, and option (b) — making the check UNRESOLVED so it follows `failureMode` — is a small code change. **Consequences, owed and not yet done:** labeller A's REVIEW labels on those four fixtures are wrong under the clarified spec and must be **re-labelled by fresh labellers, never edited by the build loop** (D-006), and the §7.3 ablation re-run afterwards.

- **D-022 (2026-08-15) — `reasonCodesHash` is documented in §5.4, and the D-010 verifier is extended to check it.** Ruled by John at the facilitated decision session, choosing options (a) and (c): *"let's follow your suggestion and go with a and c together."* **Context, because the finding shrank once measured.** The verifier reported this as its worst BLOCKER (`verifier/REPORT.md` F-3): `reasonCodesHash` unrecomputable by any third party, so a receipt carrying a substituted reason-code set would pass every check. It had in fact guessed the encoding correctly on its first family of attempts and could not match because **the receipt commits to the evaluator's codes UNIONED with the signer's own findings**, while `emit-samples.ts` had dropped the `reasonCodes` field the signer returns for exactly this purpose — a field whose own docstring reads "the exact ordered list that `reasonCodesHash` commits to, so a verifier can recompute it". A fixture omission cost an independent reviewer a blocking finding. Fixed and measured: all five samples now match `keccak256(utf8(sorted, deduped, newline-joined))`. **What was genuinely missing and is now ruled:** §5.4 documented neither the encoding nor the union semantics, and the union is the substantive half — the receipt's reason codes are NOT the evaluator's reason codes, which nobody reading §5 would guess. §5.4 is amended to state both. **Considered and rejected (option b):** committing to evaluator codes and signer findings as two separate hashed fields, so a reader can tell which layer said what without a side-channel list. Better design, but it changes the EIP-712 type string and regenerates every hash in the repository, and the audit trail is already recoverable from `signerFindings`, which the samples now publish. **Revisitable** if the audit trail proves awkward in the field.

- **D-023 (2026-08-15) — The EIP-712 type strings are published verbatim in a new §5.8, and an override sample is added. Closes the D-010 verifier's headline BLOCKER.** Ruled by John at the facilitated decision session, choosing option (b): *"I agree. Let's go with path B for this."* **The finding:** §5.1–§5.5 list bare field names, but EIP-712 needs the struct name and every field's Solidity type. §5 gave neither, so an independent implementer could not compute a single payload hash. The verifier recovered the receipt string by enumerating 3 struct names × 224 type combinations — **and the conventional uniform-`uint256` guess is in the set that failed.** It had a success oracle only because `domain.json` happens to publish `signerAddress`; without one, a wrong type string and an invalid signature are indistinguishable. **Why this was the most expensive gap:** in `abi.encode` every `uintN` occupies one left-padded word, so `uint16` and `uint256` encode identically and the width changes only the digest. There is no error and no diagnostic — the verifier reports a signer mismatch and a reasonable operator concludes the receipt is FORGED. **What recovering them bought:** before it, the CLI checked the signature and the evidence hash; after it, the whole chain — and a receipt correctly signed over the WRONG MANDATE would previously have passed, which is exactly the attack a conformance receipt exists to prevent. **Ruled:** §5.8 publishes all six strings (five payloads plus the domain), states that the payload hashes are bare EIP-712 `hashStruct` values with no `\x19\x01` prefix and no domain separator, and carries the warnings that cost the verifier real time — `uintN` width invisibility, `bytesN` right-padding, `callData` excluded from the struct, `signer` deliberately inside it, and EVM keccak256 rather than FIPS-202 SHA3-256. **`scripts/check-type-strings.sh` guards it** and is wired into the project gate: a PUBLISHED type string that has drifted from the code is worse than an absent one, because it is a confident wrong answer the implementer cannot detect. Verified to fail on drift and pass on restore. **Also ruled (the (b) half):** an override sample is added so §5.5 stops being the one payload nothing has ever verified, and the verifier's chain-binding concern is measured rather than reasoned. **Deliberately NOT taken (option c):** adding `chainId` and `vault` to `OverrideAuthorizationPayload`. The override references `mandateHash` and `policyHash`, which commit to chain and vault transitively, so the gap may be theoretical — that is what the sample is for, and a schema change on an untested hypothesis would be the wrong order.

- **D-024 (2026-08-15) — The `Verdict`, `FailureMode` and `Operation` enumerations are documented in a new §5.9, with the inversion warned about explicitly.** Ruled by John at the facilitated decision session, choosing option (a): *"Let's go with A then"*. **The finding (`verifier/REPORT.md` F-4), rated the most dangerous of the non-blockers:** the real mapping is `BLOCK = 0, REVIEW = 1, ALLOW = 2` — fail-closed, so an uninitialised or truncated field denies. That is already what the contracts and the signer do. **But every ordering in the prose implies the opposite**: §4.2 presents the cases allow-first, and §5.4 and §5.7 both say "allow, block, or review", so a reader deriving the enum from the document's own ordering gets `ALLOW = 0` — inverted, on the field §5.4 makes security-critical. **Why this outranks the other MAJORs:** `verdict` is a `uint8` inside the signed struct, so the reader's INTERPRETATION never affects the encoded bytes. A verifier holding it backwards passes the signature check, the evidence hash, and the mandate binding, then reports the opposite verdict. There is no failure mode in the cryptography that can surface it. The same unstated convention governs `failureMode` — which labeller B had to recover by cross-referencing fixture prose (A-026e), and which decides §4.2 Case 4's outcome — and `operation`. **Values verified against `contracts/src/types/SentinelTypes.sol` before publishing**, not transcribed from the report. **Considered and rejected (b):** renumbering so `ALLOW = 0` to match the prose. That destroys the fail-closed property, which is worth more than the consistency — a truncated verdict field would then mean allow. **Considered and rejected (c):** reordering §4.2 and §5.7 to present block-first. It removes the trap at its source, but §4.2's narrative ordering earns its place — a reader meets the mechanism through the conforming case — and a warning sentence buys the same safety without that cost.

- **D-025 (2026-08-15) — `PolicyPayload.allowedCallGraphHash` is RESERVED in v1, documented as not consulted. Clarifies §5.2 and §5.7.** Ruled by John at the facilitated decision session, choosing option (b): *"We'll go with B then."* **The finding (A-025a):** §5.2 declares the field and §5.7 lists "allowed top-level and internal call graph" among the supported checks, but the implementation never reads it — `EVAL_CALL_GRAPH_EXPECTED` compares against a hard-coded empty graph. **Not a defect today:** neither demo contract makes an internal call, so the empty graph IS the conforming one for both supported schemas and the check is correct on every fixture. - **A-027 (2026-08-15) — The §5.4 wording written for D-022 was itself defective, and the independent verifier caught it on the first build from it.** D-022 ruled that §5.4 document the `reasonCodesHash` construction; the text I wrote to discharge that ruling had three defects, found when the verifier implemented from it — which is exactly the test the amended wording needed and would not have received from another reading by me. **(a) A published grammar that does not hold in the language D-010 mandates.** §5.4 printed `^[A-Za-z0-9_.:-]{1,64}$` and claimed it "removes the delimiter as a source of disagreement". **Verified empirically:** in Python `re.match` that pattern accepts `"EVAL_OK\n"`, because `$` also matches before a trailing newline; in Ruby `^`/`$` are line anchors unconditionally, so `"EVIL\nINJECTED"` passes. **The consequence is a hash collision, measured not reasoned:** `{"EVIL\nINJECTED"}` and `{"EVIL", "INJECTED"}` produce the byte-identical preimage and hash to `0x5850bebd…` — one receipt committing to two different sets. - **A-011 (2026-07-27) — Signer refusal semantics: three severity tiers, and refusal never becomes a verdict.** §3.1 says the signer "confirms an allow verdict"; it does not say what happens when confirmation fails. Implemented as three tiers (`ts/src/signer/protocol.ts`). **FATAL** — the request is internally inconsistent or addressed to another system (calldata contradicts its own `dataHash`, wrong vault, wrong chain, vault unreadable, domain-separator mismatch): no receipt for any verdict. **EXECUTABILITY** — the receipt could not execute, or the vault does not recognise this signer (stale nonce, paused, expired action, simulation block not on chain): ALLOW and REVIEW refused, BLOCK still signed, because a block receipt is evidence rather than authority. **CONFORMANCE** — a finding the evaluator was supposed to weigh (code-hash mismatch, mandate/policy window, value ceiling, stale binding): ALLOW refused per §3.3(8), REVIEW permitted. **That last permission is load-bearing, not laxity:** Case 4's triggers are exactly these conditions and its expected result is a REVIEW receipt, so a signer that refused here would make a ratified demonstration case unreachable while appearing stricter. **Corrected 2026-07-27 after adversarial review:** the first implementation got this right for the code-hash trigger and wrong for its sibling in the same sentence of §4.2 — "the anchored RPC state conflicts, or simulation is unavailable" was tiered EXECUTABILITY, which refuses REVIEW, so half of Case 4 could never produce the receipt the spec requires. `SIGNER_SIMULATION_BLOCK_MISMATCH` is now CONFORMANCE, and the rule the mistake yielded is recorded beside it: a check whose subject is *evidence quality* belongs in CONFORMANCE, because "we cannot confirm this" is what a review verdict is for; EXECUTABILITY is only for facts that make a receipt unusable. A test asserts the whole CONFORMANCE tier permits REVIEW, rather than one example of it. Second half of the ruling: on a failed check the signer **refuses**; it never downgrades an ALLOW into a signed BLOCK. "Sentinel evaluated this and blocked it" and "the signer declined to attest" are different claims, and an evidence bundle that conflates them misreports what the system concluded. **Revisitable — flagged to John as a call he may want to take back**, because it decides what artifacts exist in the S2 evidence bundle.
- **A-012 (2026-07-27) — One live executable attestation per (chain, vault, nonce).** A guarantee the spec does not require, added because the vault structurally cannot provide it. Nonce consumption makes any single credential single-use (§3.3(9)), but nothing stopped the signer issuing two *different* valid ALLOW receipts for the same nonce before either executed; both are well-formed credentials, whoever relays first wins, and the owner authorised only one. The signer refuses the second unless it names the same action (idempotent re-sign, so a lost response cannot wedge the nonce) or the prior attestation has expired. BLOCK receipts do not hold the nonce. **Narrowed 2026-07-27 after adversarial review, in two ways.** (a) The reservation is scoped to the *authorisation basis* — the active mandate and policy hashes it was taken under — and is void once either changes. Without this, a REVIEW receipt the owner declined to override held the nonce for its whole TTL, refusing the corrected action taken under a new mandate: §4.2 Case 4's second stated remedy, "or a new mandate". Two credentials can never be live under two different active mandate hashes (the vault reverts `MandateNotActive` on the stale one), so the narrowing is strictly safe rather than a trade. (b) An idempotent re-sign may never *shorten* a live reservation: `ttlSeconds` is a caller field, and a retry with a small TTL would otherwise free the nonce while the receipt already issued was still valid. **Explicitly considered and rejected:** exempting REVIEW from reserving at all. - **A-014 (2026-07-27) — Signer RPC shape.** Unix domain socket at mode 0600 rather than a loopback TCP port (a port is reachable by every local process and by anything that can aim a browser at 127.0.0.1); newline-delimited JSON rather than HTTP (no routing, headers, or content negotiation to reason about); exactly two methods, `status` and `evaluateAndSign`. - **A-017 (2026-07-28) — Decoder design (§9 step 4).** (a) **Strict, hand-rolled word reading rather than a library decoder.** §4.2 Case 2 turns on Sentinel deriving parameters from calldata rather than from the agent's description; that derivation is only worth something if calldata which is *almost* well-formed is refused rather than silently normalised. Every deviation is a named failure code, and all eight are triggered by their own test with a structural exhaustiveness assertion so a ninth cannot arrive untested. (b) **Target binding is part of decoding.** A `purchase` selector aimed at DemoERC20 is not a purchase; the decoder is told which contract is at which address and refuses the mismatch rather than decoding parameters describing a call that cannot happen (§3.3(11)). (c) **The decoder renders no verdict.** It turns bytes into typed parameters or fails with a reason; comparing those parameters against the signed mandate is the conformance evaluator's job (§9 step 6). Keeping the split means the decoder can be tested for faithfulness-to-bytes alone, and a decoding bug cannot pollute the evaluator's results against the labelled corpus. (d) **Selectors pinned beside their transcribed signatures** and checked at import, the same technique as the EIP-712 golden typehashes and for the same reason. **Measured, not assumed:** `decode.chain.test.ts` compares the decoder against the compiled contracts on a live EVM. - **A-019 (2026-07-28) — Effect-pipeline design (§9 step 5).** (a) **The revert is in a `finally`, and a failed revert throws `SimulationLeakError` rather than returning.** A leaked simulation does not produce one wrong answer; it corrupts every later result on the same chain, order-dependently, which is the hardest kind of wrong to notice in a green suite. The fixture corpus depends on this property, so it is asserted directly — including on the revert path, where a `finally` that only runs on success is the classic bug. (b) **The simulation executes as the VAULT, via `anvil_impersonateAccount`.** `DemoPay.purchase` records `buyer = msg.sender` and `DemoERC20.approve` sets `allowance[msg.sender][spender]` — which is exactly why the Case 2 injection is dangerous. Simulating from any other sender would measure an allowance nobody can spend and score the attack harmless. **The test for this was initially vacuous**: it used an Anvil dev account as the vault stand-in, so the node signed natively and impersonation was dead code that a mutation could remove unnoticed. It now deploys and impersonates the real `SentinelVault` contract, for which no node holds a key. (c) **Gas is zeroed for the simulation** (`anvil_setNextBlockBaseFeePerGas` to 0, `gasPrice` 0), because in production a relayer submits the receipt and pays gas while the vault's balance moves by the forwarded value alone. Measured rather than assumed: at the default base fee an impersonated sender's delta was −42000000001000 for a 1000 wei transfer; zeroed, it is exactly −1000. Without this the native-balance delta is not the value transfer and every comparison against `maxNativeValueWei` is off by a gas-price-dependent amount. (d) **The vault is never topped up.** No `setBalance` on the account under test — an unfunded vault must show its revert rather than have a real failure converted into a fabricated success. (e) **`unresolvedChecks` travels.** A missing call trace is recorded as `SIM_CALL_TRACE_UNAVAILABLE`, never collapsed into "no internal calls"; §3.3(8) requires a critical dependency failure never produce an automatic allow, and those two facts must not reach the evaluator as the same one. **Claims boundary:** these are simulated effects at a recorded block (§8 as amended by D-001), and the recorded anchor — which survives the revert, and which the isolated signer independently re-checks — is what makes that claim auditable rather than rhetorical.
- **A-020 (2026-07-28) — Reading of §5.2 "any unknown required check reviews" against `PolicyPayload.failureMode`.** §5.2's prose says an unknown required check reviews; the schema also carries `failureMode ∈ {FAIL_CLOSED, REVIEW}`, described as the behaviour when a required check cannot be evaluated. Read together, the prose describes the REVIEW setting and the field parameterises it. **The field governs**, and the consequence is stated because it shapes the demo: §4.2 Case 4 expects a REVIEW receipt, so the Case 4 policy must set `failureMode = REVIEW`. Under FAIL_CLOSED the identical evidence uncertainty blocks — a legitimate configuration and a different demonstration. Both are asserted as tests, so the engine is visibly not hard-coding Case 4's outcome. **This is a spec-interpretation call rather than an engineering one; flagged for John.** The alternative reading — prose is normative, `failureMode` governs only some other class of failure — would make the field nearly meaningless, which is why it was not taken. Related and settled inside the same reading: a **target code-hash mismatch is UNRESOLVED, not a VIOLATION**, because §4.2 says "Sentinel does not label the target malicious. It reports insufficient evidence for automatic approval." Classifying it as a violation would hard-block Case 4 and would assert something about the target that Sentinel has not established. §3.3(8) is consistent: it lists code-identity mismatch among conditions that never produce an *automatic allow*, a bar UNRESOLVED already clears.
- **A-021 (2026-07-28) — The mutation harness destroyed `ts/src`, and what changed as a result.** The harness backed up the whole source tree and restored it with `rm -rf src; cp -R backup src`. When a sweep outgrew its 10-minute budget and was killed mid-restore, `ts/src` was left **empty**. Nothing was ultimately lost — the suite returned to the identical 161/161 — but the exposure was real and it was created by a tool whose whole purpose is to leave the tree as it found it. **Three changes, in order of importance.** (a) The harness now backs up and restores exactly ONE file per mutation, so there is no instant at which the tree is missing anything; a kill at the worst possible moment leaves at most one modified file. (b) It traps TERM and INT as well as EXIT, because a timeout kill arrives as TERM and that is precisely the case that failed. (c) It refuses to run against a dirty `ts/src`, which both keeps results interpretable and makes `git checkout --` a reliable fallback. **The generalisable lesson, worth more than the fix: a repair tool must never have a window in which the thing it repairs does not exist.** The secondary lesson is that uncommitted work is the only work that cannot be recovered — commit before running anything destructive, not after.
