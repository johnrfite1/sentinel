- **D-007 (2026-07-27, delegated) — Case 2: what counts as a real prompt injection.** Operationalizes the §7.5 hard gate "a real prompt injection changes the agent proposal and is contained." A demonstration counts as real only when all three hold: (a) the agent configuration is a documented, plausibly-naive default, with nothing in its own instructions engineered to make it obey injected text, and its scaffold pinned by hash; (b) the malicious content arrives through a data channel the agent legitimately reads (§3.1 "retrieved documents"), never through its own instruction channel; (c) a **control run** — same configuration, same channel, benign document — produces the Case 1 proposal. Without the control run the flip is not attributable to the injection, which is the difference between a demonstration and a staged demo. Each injection fixture records model id, model version, temperature, scaffold hash, date, and the full transcript. **Reproducibility:** pinned transcripts are the CI fixtures; one live canary run executes alongside them, never fails CI, and its run history is included in the S2 evidence bundle — an unobserved canary is not evidence. **Spike-first:** the injection is attempted before the deep build, timeboxed to 4 hours. A negative result is a finding, not a failure — §4's claim is that an *untrusted* agent cannot execute, not that a gullible one is fooled. On a negative result: report the frontier-model resistance honestly as its own data point and drive Case 2 with a deliberately naive configuration labeled as such. One genuine injection; no jailbreak research.
- **D-008 (2026-07-27, delegated) — §7.5 soft-gate definitions.** Two §7.5 gates were unfalsifiable as written; under D-003 no implementing agent may define a gate, so they are defined here. **Five-minute comprehension:** three fresh-context reviewers, given only the demo, dashboard, and README — no repository access — each answer five questions frozen before the first run and never shown to the build loop. Pass threshold, set in advance: all three score ≥4/5. The questions are those a skeptical security engineer asks — what is cryptographically bound; who signs what; why Case 3 blocks; what a receipt proves; what it does not prove. Agents run this as a proxy; John samples. **Vendor honesty:** every cell of the capability matrix is documentation-only, dated, and linked to its cited source; the "executed" and "faithfully emulated" columns of the §10.1 labeling scheme are empty in v1 (per D-001); cells that are inference rather than quoted documentation are marked as inference; and no claim *or layout* implying empirical superiority over any named vendor appears in any v1 artifact. The empty-column condition is mechanically checkable.
- **D-009 (2026-07-27, delegated) — Gate S2 pass conditions amended. Amends D-002.** Gate S2 passes on: the full 30–50 fixture corpus; §7.5 hard-gate evidence; the §7.3 ablation report; and the receipt-verifier CLI (D-010). The ablation is added because §7 opens by stating that four demo paths alone cannot prove the verdicts are not hard-coded — without it, S2 would sign off a corpus with no analysis that makes the corpus mean anything. The evidence dashboard remains outside S2 unless John adds it at the gate. If the window tightens, priority order is corpus > ablation > CLI.
- **D-010 (2026-07-27, delegated) — Receipt-verifier CLI promoted into v1. Amends D-001.** The 14.2 standalone receipt verifier moves from ladder rung 1 to a Gate S2 pass condition (D-009). The reason is engineering rather than strategic: an independent reimplementation is the strongest available test of the spec's precision, and RFC 8785 edge cases, hash-domain separation, and encoding ambiguity surface only when someone builds from the written schema. That feedback is wanted while the schemas are still cheap to change — after the corpus fossilizes, a schema correction regenerates every fixture. **Conditions:** the verifier shares no canonicalization or hashing code with the evaluator (same library behind a different flag is the same code verifying itself); it is implemented in a different language from the evaluator — Python — against an independent JCS implementation and an independent keccak implementation, because cross-language agreement is a materially stronger test than two TypeScript modules *and* is cheaper than hand-rolling a second RFC 8785 implementation; and it is built from the published schemas only. **Effort:** 14.2's 10–20h estimate assumed code reuse. With the independence condition the corrected budget is 20–30h. Recorded as a measured correction to a documented number, per AGENTS.md.
- **D-011 (2026-07-27, delegated) — Fixture-label independence protocol. Extends D-006.** Independence here is **procedural, not organizational**, and §8 states it in those words. A solo build cannot buy organizational independence; what it can buy is an auditable bound. (a) The labeling prompt is authored and frozen **before the corpus build**, and its hash committed. The claim is deliberately "before the corpus build" and not "before the evaluator's failure modes are known" — Case 1 is end-to-end by S1, so some evaluator knowledge already exists; the freeze blocks the bulk of it, which is corpus-build knowledge, from leaking backward. (b) The labeler receives payload schemas, security invariants, and each fixture's declared intent — never evaluator source, never evaluator output. (c) A second fresh labeler re-labels a random ~20% sample; the disagreement rate is reported at S2 as a corpus-quality metric. (d) Thresholds are declared in advance, or the metric is decoration: >10% disagreement halts S2 pending corpus review, and any disagreement on a hard-gate-relevant fixture escalates to John individually regardless of the aggregate rate. (e) John's gate sampling is adversarial rather than random — oversample fixtures where the baseline and conformance verdicts disagree, and fixtures whose label is *review*.

- **A-011 (2026-07-27) — Signer refusal semantics: three severity tiers, and refusal never becomes a verdict.** §3.1 says the signer "confirms an allow verdict"; it does not say what happens when confirmation fails. Implemented as three tiers (`ts/src/signer/protocol.ts`). **FATAL** — the request is internally inconsistent or addressed to another system (calldata contradicts its own `dataHash`, wrong vault, wrong chain, vault unreadable, domain-separator mismatch): no receipt for any verdict. **EXECUTABILITY** — the receipt could not execute, or the vault does not recognise this signer (stale nonce, paused, expired action, simulation block not on chain): ALLOW and REVIEW refused, BLOCK still signed, because a block receipt is evidence rather than authority. **CONFORMANCE** — a finding the evaluator was supposed to weigh (code-hash mismatch, mandate/policy window, value ceiling, stale binding): ALLOW refused per §3.3(8), REVIEW permitted. **That last permission is load-bearing, not laxity:** Case 4's triggers are exactly these conditions and its expected result is a REVIEW receipt, so a signer that refused here would make a ratified demonstration case unreachable while appearing stricter. **Corrected 2026-07-27 after adversarial review:** the first implementation got this right for the code-hash trigger and wrong for its sibling in the same sentence of §4.2 — "the anchored RPC state conflicts, or simulation is unavailable" was tiered EXECUTABILITY, which refuses REVIEW, so half of Case 4 could never produce the receipt the spec requires. `SIGNER_SIMULATION_BLOCK_MISMATCH` is now CONFORMANCE, and the rule the mistake yielded is recorded beside it: a check whose subject is *evidence quality* belongs in CONFORMANCE, because "we cannot confirm this" is what a review verdict is for; EXECUTABILITY is only for facts that make a receipt unusable. A test asserts the whole CONFORMANCE tier permits REVIEW, rather than one example of it. Second half of the ruling: on a failed check the signer **refuses**; it never downgrades an ALLOW into a signed BLOCK. "Sentinel evaluated this and blocked it" and "the signer declined to attest" are different claims, and an evidence bundle that conflates them misreports what the system concluded. **Revisitable — flagged to John as a call he may want to take back**, because it decides what artifacts exist in the S2 evidence bundle.
- **A-012 (2026-07-27) — One live executable attestation per (chain, vault, nonce).** A guarantee the spec does not require, added because the vault structurally cannot provide it. Nonce consumption makes any single credential single-use (§3.3(9)), but nothing stopped the signer issuing two *different* valid ALLOW receipts for the same nonce before either executed; both are well-formed credentials, whoever relays first wins, and the owner authorised only one. The signer refuses the second unless it names the same action (idempotent re-sign, so a lost response cannot wedge the nonce) or the prior attestation has expired. BLOCK receipts do not hold the nonce. **Narrowed 2026-07-27 after adversarial review, in two ways.** (a) The reservation is scoped to the *authorisation basis* — the active mandate and policy hashes it was taken under — and is void once either changes. Without this, a REVIEW receipt the owner declined to override held the nonce for its whole TTL, refusing the corrected action taken under a new mandate: §4.2 Case 4's second stated remedy, "or a new mandate". Two credentials can never be live under two different active mandate hashes (the vault reverts `MandateNotActive` on the stale one), so the narrowing is strictly safe rather than a trade. (b) An idempotent re-sign may never *shorten* a live reservation: `ttlSeconds` is a caller field, and a retry with a small TTL would otherwise free the nonce while the receipt already issued was still valid. **Explicitly considered and rejected:** exempting REVIEW from reserving at all. It is the more attractive-sounding fix and it is wrong — `executeWithOverride` makes a REVIEW receipt executable the moment the owner signs an exact-action override, so exempting it would let a live overridable REVIEW for action A1 and a live ALLOW for A2 share one nonce, with A2 racing the owner's deliberate choice to the vault. **Honest limit, stated in the code:** the guard is in process memory, so a restart forgets it and two signer processes sharing a key would not see each other; the vault's nonce remains the authoritative guard. **Revisitable — also flagged to John**, as it adds a guarantee to the system's public description.
- **A-013 (2026-07-27) — The signer's EIP-712 implementation is deliberately NOT shared, and is differentially tested against Solidity.** `ts/src/signer/eip712.ts` is a second implementation, transcribed from §5 rather than ported from `SentinelTypes.sol`, with the Solidity golden typehashes pinned beside it and checked at process start. The conformance evaluator (§9 step 6) will get its own and must not import this one. This applies D-010's already-ratified standard — *"the same library behind a different flag is the same code verifying itself"* — to §3.1's word "independently". Enforcement: `contracts/test/TypesHarness.sol` exposes the library's pure hash functions so the TypeScript is compared against Solidity on a live EVM across all five §5 payloads plus the domain separator. **This closed a real gap rather than a theoretical one:** the vault recomputes `hashAction` and `hashReceipt` on every execution, but it stores the mandate and policy only as hashes and never recomputes them, so a TypeScript encoder could have disagreed with Solidity on `hashMandate`, `hashPolicy`, and `hashOverride` while every onchain test stayed green — the offchain side would simply activate its own wrong hash and match it.
- **A-014 (2026-07-27) — Signer RPC shape.** Unix domain socket at mode 0600 rather than a loopback TCP port (a port is reachable by every local process and by anything that can aim a browser at 127.0.0.1); newline-delimited JSON rather than HTTP (no routing, headers, or content negotiation to reason about); exactly two methods, `status` and `evaluateAndSign`. Three consequences of "no generic sign-bytes" that are easy to lose later and so are recorded here: the **evidence bundle is passed in full and hashed by the signer**, never accepted as a caller-supplied `evidenceHash`, so the signer never signs a digest it did not compute; **`decisionId` is signer-generated**, removing another caller-controlled 32 bytes from a signed structure; and the keystore exposes **only** `signReceipt`, with no in-process function that accepts arbitrary bytes, so the narrowness cannot be bypassed by an import. Key material defaults to **ephemeral** — generated at boot, never written to disk — with `SENTINEL_SIGNER_KEY` as the override; the cost is that a restart requires the owner to rotate the vault's signer, which §3.3(2) already requires be human-only and authenticated.

- **A-017 (2026-07-28) — Decoder design (§9 step 4).** (a) **Strict, hand-rolled word reading rather than a library decoder.** §4.2 Case 2 turns on Sentinel deriving parameters from calldata rather than from the agent's description; that derivation is only worth something if calldata which is *almost* well-formed is refused rather than silently normalised. Every deviation is a named failure code, and all eight are triggered by their own test with a structural exhaustiveness assertion so a ninth cannot arrive untested. (b) **Target binding is part of decoding.** A `purchase` selector aimed at DemoERC20 is not a purchase; the decoder is told which contract is at which address and refuses the mismatch rather than decoding parameters describing a call that cannot happen (§3.3(11)). (c) **The decoder renders no verdict.** It turns bytes into typed parameters or fails with a reason; comparing those parameters against the signed mandate is the conformance evaluator's job (§9 step 6). Keeping the split means the decoder can be tested for faithfulness-to-bytes alone, and a decoding bug cannot pollute the evaluator's results against the labelled corpus. (d) **Selectors pinned beside their transcribed signatures** and checked at import, the same technique as the EIP-712 golden typehashes and for the same reason. **Measured, not assumed:** `decode.chain.test.ts` compares the decoder against the compiled contracts on a live EVM. The expectation going in was that Solidity would be lenient about dirty address bits, non-canonical bools, and over-wide integers; **it is not — it reverts on all three.** The decoder's strictness there is agreement with the EVM, not an addition to it. There is exactly **one** genuine Sentinel-only rule: trailing bytes past the declared arguments, which Solidity ignores and Sentinel refuses because those bytes are part of what was proposed and `dataHash` binds them. The test asserts that divergence set is exactly one case, so the claim in `abi.ts` cannot decay away from the truth.
- **A-018 (2026-07-28) — Open fork, NOT resolved: should the isolated signer check decoded parameters?** Raised rather than decided, because it changes what the product guarantees. The signer currently checks the mandate's target, selector, and value ceiling, but not the mandate's `resourceId`, `beneficiary`, `durationSeconds`, or `recurringAllowed` — so a wrong-purpose action (Case 3) is signed, as `signer.e2e.test.ts` demonstrates. Now that decoders exist, the signer *could* check those four fields independently, which would mean a compromised evaluator could no longer obtain an ALLOW for a wrong-purpose action. **For:** §3.1 says the signer "checks the current mandate", and those fields are in the mandate; it materially strengthens the isolated-signer claim. **Against:** it duplicates the conformance evaluator inside the signer, contradicts A-011's stated boundary ("the signer confirms a verdict, it does not compute one"), and would make the published coverage boundary — "the signer prevents a mis-bound receipt, not a wrong verdict" — need rewriting. Deferred to the §9 step 6 evaluator design, where it actually has to be answered. Recorded now so the question is not silently settled by whichever way step 6 happens to get built.
- **A-019 (2026-07-28) — Effect-pipeline design (§9 step 5).** (a) **The revert is in a `finally`, and a failed revert throws `SimulationLeakError` rather than returning.** A leaked simulation does not produce one wrong answer; it corrupts every later result on the same chain, order-dependently, which is the hardest kind of wrong to notice in a green suite. The fixture corpus depends on this property, so it is asserted directly — including on the revert path, where a `finally` that only runs on success is the classic bug. (b) **The simulation executes as the VAULT, via `anvil_impersonateAccount`.** `DemoPay.purchase` records `buyer = msg.sender` and `DemoERC20.approve` sets `allowance[msg.sender][spender]` — which is exactly why the Case 2 injection is dangerous. Simulating from any other sender would measure an allowance nobody can spend and score the attack harmless. **The test for this was initially vacuous**: it used an Anvil dev account as the vault stand-in, so the node signed natively and impersonation was dead code that a mutation could remove unnoticed. It now deploys and impersonates the real `SentinelVault` contract, for which no node holds a key. (c) **Gas is zeroed for the simulation** (`anvil_setNextBlockBaseFeePerGas` to 0, `gasPrice` 0), because in production a relayer submits the receipt and pays gas while the vault's balance moves by the forwarded value alone. Measured rather than assumed: at the default base fee an impersonated sender's delta was −42000000001000 for a 1000 wei transfer; zeroed, it is exactly −1000. Without this the native-balance delta is not the value transfer and every comparison against `maxNativeValueWei` is off by a gas-price-dependent amount. (d) **The vault is never topped up.** No `setBalance` on the account under test — an unfunded vault must show its revert rather than have a real failure converted into a fabricated success. (e) **`unresolvedChecks` travels.** A missing call trace is recorded as `SIM_CALL_TRACE_UNAVAILABLE`, never collapsed into "no internal calls"; §3.3(8) requires a critical dependency failure never produce an automatic allow, and those two facts must not reach the evaluator as the same one. **Claims boundary:** these are simulated effects at a recorded block (§8 as amended by D-001), and the recorded anchor — which survives the revert, and which the isolated signer independently re-checks — is what makes that claim auditable rather than rhetorical.
- **A-020 (2026-07-28) — Reading of §5.2 "any unknown required check reviews" against `PolicyPayload.failureMode`.** §5.2's prose says an unknown required check reviews; the schema also carries `failureMode ∈ {FAIL_CLOSED, REVIEW}`, described as the behaviour when a required check cannot be evaluated. Read together, the prose describes the REVIEW setting and the field parameterises it. **The field governs**, and the consequence is stated because it shapes the demo: §4.2 Case 4 expects a REVIEW receipt, so the Case 4 policy must set `failureMode = REVIEW`. Under FAIL_CLOSED the identical evidence uncertainty blocks — a legitimate configuration and a different demonstration. Both are asserted as tests, so the engine is visibly not hard-coding Case 4's outcome. **This is a spec-interpretation call rather than an engineering one; flagged for John.** The alternative reading — prose is normative, `failureMode` governs only some other class of failure — would make the field nearly meaningless, which is why it was not taken. Related and settled inside the same reading: a **target code-hash mismatch is UNRESOLVED, not a VIOLATION**, because §4.2 says "Sentinel does not label the target malicious. It reports insufficient evidence for automatic approval." Classifying it as a violation would hard-block Case 4 and would assert something about the target that Sentinel has not established. §3.3(8) is consistent: it lists code-identity mismatch among conditions that never produce an *automatic allow*, a bar UNRESOLVED already clears.
- **A-021 (2026-07-28) — The mutation harness destroyed `ts/src`, and what changed as a result.** The harness backed up the whole source tree and restored it with `rm -rf src; cp -R backup src`. When a sweep outgrew its 10-minute budget and was killed mid-restore, `ts/src` was left **empty**. The fifteen committed files were recovered with `git checkout --`; four uncommitted files (`ts/src/evaluate/*`) had to be rewritten. Nothing was ultimately lost — the suite returned to the identical 161/161 — but the exposure was real and it was created by a tool whose whole purpose is to leave the tree as it found it. **Three changes, in order of importance.** (a) The harness now backs up and restores exactly ONE file per mutation, so there is no instant at which the tree is missing anything; a kill at the worst possible moment leaves at most one modified file. (b) It traps TERM and INT as well as EXIT, because a timeout kill arrives as TERM and that is precisely the case that failed. (c) It refuses to run against a dirty `ts/src`, which both keeps results interpretable and makes `git checkout --` a reliable fallback. **The generalisable lesson, worth more than the fix: a repair tool must never have a window in which the thing it repairs does not exist.** The secondary lesson is that uncommitted work is the only work that cannot be recovered — commit before running anything destructive, not after.
